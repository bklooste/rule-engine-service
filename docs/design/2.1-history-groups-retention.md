# Design: transactional history, per-pattern retention, group writes, readable ended rules (2.1)

Status: proposed, for the owner's review before any code. Target release: **2.1.0** (minor: every change is
additive on the wire; the two behaviour changes are listed under "Compatibility").

This note decides how four changes are built. They were asked for by a consumer that keeps money-bearing
definitions (promotions) in templates and needs the history to be an audit record, not a convenience:

| # | Change | Built as |
|---|---|---|
| L1 | A committed version always has its snapshot | One commit primitive: document, counter, snapshot and version metadata in one `MULTI` ([D1](#d1-one-commit-primitive-l1)) |
| L2 | History retention per template id pattern | Ordered `TemplateHistory:Rules`, first match wins ([D4](#d4-retention-per-template-id-pattern-l2)) |
| L3 | Write, list history of, and roll back one `group` of rules | `v2/templates/{id}/groups/{group}` routes over a per-document group index ([D3](#d3-version-metadata-and-the-group-index), [D5](#d5-group-routes-l3)) |
| L4 | Ended rules stay stored and listable for a while | `ExpiredRuleRetentionDays`, applied on write; `?includeExpired=true` on reads ([D6](#d6-ended-rules-l4)) |

Implementation order: L1 first (every later change writes through its commit primitive), then L2 and L4 in
either order, L3 after L1. Each step's tests are listed under [Tests](#tests-per-step).

## How it works today (v2.0.4)

Read from the source; these are the facts the decisions below rest on.

- **Keys** (all under the prefix `Templates:KeyPrefix`, default `{ENVIRONMENT}:plat-templates:`; `K` below is
  `Templates:TenantKeyFormat` with the id substituted, default `{id}-templates`):
  `K` the current document, `K:version` the counter, `K:v{n}` the snapshot of version n, `K:versions` a sorted
  set of version numbers scored by write time (unix seconds), and `templates:index` the set of ids.
- **Writes.** `Repository.SetAsync` (no `If-Match`, also used by rollback) and `SetIfVersionAsync` (with
  `If-Match`, also used by the rule-level routes) run `SET K`, `INCR K:version`, `SADD templates:index` in one
  transaction. `SetIfVersionAsync` adds the condition `K:version == expected`. The new version number is
  `INCR`'s result, known only after `EXEC`.
- **History.** `SaveVersionSnapshotAsync` then writes `K:v{n}` and `ZADD K:versions` in a *second*
  transaction ("best-effort history"), and `PruneOldVersionsAsync` deletes every snapshot whose write time is
  older than `TemplateHistory:RetentionDays` (default 90, and `<= 0` is treated as 1 day). A crash, a dropped
  connection or a timeout between the two transactions leaves version n with no snapshot.
- **Two history bugs found while reading.**
  1. Prune deletes by *write* time, so the version that was in force at the start of the window is deleted.
     If v5 was written 100 days ago and v6 is written now, the write of v6 prunes v5: the version in force
     until a moment ago is gone, and "roll back my last edit" fails.
  2. `RollbackAsync` re-writes the old snapshot as it was, so the new version's `changedBy` is the *old*
     version's author, not the caller of the rollback.
- **Ended rules.** `DynamicTemplate.IsExpired` (`expiresAt <= now`) is skipped on evaluate
  (`DynamicRulesEngine`) and reported in explain; `V2Logic.Prune` hides it on `GET v2/templates/{id}`;
  `MutateRulesAsync` (rule `PUT`/`DELETE`) drops it from the stored document. A whole-document `PUT` stores
  whatever the body holds. `GET .../rules/{name}` and `GET .../versions/{n}` return ended rules unfiltered.
- **Groups.** `DynamicTemplate.Group` is stored and round-trips. Nothing reads or writes by it.
- **Concurrency.** The document ETag is its version. The rule ETag is a content hash (first 16 hex of SHA-256
  of the serialized rule), so a rule edit conflicts only with an edit to the same rule; a lost version race on
  a rule write is retried `RuleWriteAttempts` (4) times, then `409`.

## D1. One commit primitive (L1)

Every write path goes through one repository method:

```csharp
// null = the version moved since `observedVersion` was read; the caller re-reads and retries.
Task<long?> CommitAsync(string id, Template next, long observedVersion, IReadOnlyCollection<string> changedGroups);
```

**The version number is known before the transaction starts.** The commit is always conditional on the
version the writer read: `K:version == observedVersion`, or `K:version` does not exist when `observedVersion`
is 0 (counters start at 1, and a deleted document keeps its counter, so 0 means "never written"). If the
transaction commits, nothing else moved the counter in between, so the new version is exactly
`n = observedVersion + 1`, and the snapshot key `K:v{n}` can be named inside the same transaction. That
removes the only reason the snapshot was written afterwards.

One `MULTI`/`EXEC`, guarded by the condition above (StackExchange.Redis implements it with `WATCH`):

```
SET    K                 <document json>
INCR   K:version                                   -- asserted == n after EXEC; anything else throws
SADD   templates:index   <id>
SET    K:v{n}            <document json>           -- the same bytes as K
ZADD   K:versions        <write time, unix s>  n
HSET   K:vmeta           n  {"updatedAt","changedBy","groups":[...changedGroups]}
ZADD   K:gidx            0  "<group>\0<n as 19 digits>"   -- one per changed group (D3)
```

Pruning (D4) stays a separate, later transaction. A failed or skipped prune leaves *more* history, never
less, so it may stay best effort.

**Every writer becomes read, decide, conditional commit, retry.** `SetAsync`'s unconditional path goes away:

| Route | Read | Retry a lost version race? |
|---|---|---|
| `PUT v2/templates/{id}`, no `If-Match` or `If-Match: *` | current document and version | yes, up to `RuleWriteAttempts`, then `409` |
| `PUT v2/templates/{id}`, `If-Match: "n"` | current document; `412` unless its version is n | no: a race is a `412`, as today |
| rule `PUT`/`DELETE` | as today (`MutateRulesAsync`) | yes, as today |
| group `PUT`/`DELETE`/rollback (D5) | current document | yes, same loop |
| `POST .../rollback/{n}` | snapshot n and the current document | yes, same loop |

The read before the commit is needed anyway: the group index (D3) is the diff between the stored document and
the new one, and only a conditional commit guarantees that the stored document is the one that was diffed.

**Why not a Lua script.** A script could `INCR` and then `SET` the key it computed, with no retry. It cannot
compute the changed groups without the previous document, which the diff needs, and it puts the commit logic
in a second language. The retry loop already exists for rule writes.

### A3: the assumption this design rests on, and its result

> **Assumption.** L1 fits inside the existing `MULTI` that moves the version pointer. Falsified if the
> snapshot write cannot join that transaction (for example it goes to a different Redis connection or store).
> In that case L1 becomes "write the snapshot first, then commit the pointer", with a sweep for orphaned
> snapshots.

**Result: the assumption holds; the fallback is not taken.** From the source:

- The snapshot goes through the same `IDatabase` as the document (`Repository.dbFunc`: one
  `ConnectionMultiplexer`, the same database, the same `WithKeyPrefix` wrapper). There is no second store.
- The one obstacle is that the snapshot key needs the new version number. D1 removes it by making every commit
  conditional on the observed version, so `n = observed + 1` is known before `MULTI`.
- The existing transaction already spans unrelated keys (`K` and `templates:index`), so the service already
  requires a Redis where one transaction may touch any key (standalone, or a proxy that allows it). Adding
  `K:v{n}`, `K:versions`, `K:vmeta` and `K:gidx` adds no new requirement. A Redis Cluster deployment would
  already fail today with `CROSSSLOT`.

What A3 does not cover, written down so nobody assumes it:

- **Redis transactions do not roll back.** `EXEC` either runs every queued command or none (a command that
  fails to queue, including an out-of-memory refusal, aborts the whole `EXEC`). A command that fails *while
  running* does not undo the others. Here that can only be a type error on a key holding the wrong type,
  which means the keyspace was corrupted by something other than this service. `SET` cannot fail that way;
  the `ZADD`/`HSET` lines can only fail that way.
- **Eviction.** Under `maxmemory-policy allkeys-*` Redis may evict a snapshot later. History is durable only
  on a Redis with `noeviction` (or a `volatile-*` policy, since these keys carry no TTL). The README gains this
  as a deployment requirement.
- **A lost reply.** If the connection drops after Redis ran `EXEC` but before the reply arrives, the client
  sees an error although both the document and its snapshot are stored. That is "both", which L1 allows. A
  retried group write is then a no-op (D5); a retried whole-document `PUT` writes one more identical version.

## D2. Version numbering

- One counter per document, as today. Every committed write of any kind (document, rule, group, either
  rollback, a write that only drops ended rules as a side effect) adds exactly one version.
- **Groups have no counter of their own.** "Version n of group g" means "document version n", and a group's
  history is the list of document versions that changed it. A group rollback target `n` is a document
  version, so a caller can roll a group back to any retained version, including one that did not touch the
  group (the group is restored as it stood then).
- **A no-op group write commits nothing.** If a group `PUT` asks for exactly the rules the group already has,
  it returns `200` with the current version and adds no version. This makes a client's retry of a group write
  idempotent. Document `PUT` and rule writes keep today's behaviour (always a new version).
- Versions are never renumbered or reused. Deleting a document keeps (and bumps) its counter, as today.

## D3. Version metadata and the group index

`GET .../groups/{group}/versions` must list the versions that changed a group without reading every snapshot
(a snapshot is the whole document; the motivating consumer's documents are around 300 KB). Two new keys per
document, both written in the commit transaction (D1):

| Key | Type | Content |
|---|---|---|
| `K:vmeta` | hash | field `n` → `{"updatedAt", "changedBy", "groups": [...]}`, the summary of version n and the groups it changed |
| `K:gidx` | sorted set, every score 0 | member `"<group>\0<n zero-padded to 19 digits>"` for each (changed group, version) |

**Lookup.** A group's versions, newest first, are one `ZREVRANGEBYLEX K:gidx "(<group>\x01" "[<group>\0"`, then
one `HMGET K:vmeta` for the summaries. `\0` sorts below every other byte, so the range holds exactly that group's
members, and the 19-digit padding makes lexical order version order. Cost is O(log N + M) for M results.
Group names are validated (non-empty, at most 256 characters, no control characters), so `\0` cannot occur in
one.

**Why one sorted set per document and not one per group.** Deleting a document and pruning a version each
touch a known, fixed set of keys (`K:gidx` and `K:vmeta`), with no need to enumerate groups to find their
keys, and the key count does not grow with the number of groups.

**What counts as "changed group g".** Computed by the writer, inside the retry loop, by comparing the stored
document it read with the document it is about to commit (after D6 has dropped ended rules):

- A group's content is the ordered list of the rules whose `group` is g. It changed if the two lists differ
  (compared by the rule content hash already used for rule ETags).
- This covers every write path, not just the group routes: a whole-document `PUT`, a rule `PUT` that edits a
  grouped rule or moves a rule between groups, a whole-document rollback, and a write that drops another
  group's ended rules (D6). Indexing only the group routes would silently leave holes in a group's history,
  which is the failure this design must not have.
- Rules with no `group` are not indexed. They appear only in the document's own history.

**The `K:vmeta` hash also makes `GET v2/templates/{id}/versions` cheap.** Today it fetches every snapshot to
read `updatedAt` and `changedBy`. With `K:vmeta` it reads the hash, and falls back to the snapshot only for a
version written before 2.1 (no field). `TemplateVersionSummary` gains an optional `groups` array (omitted when
unknown), so the history list says which groups each version touched. Both history lists take optional
`?limit=` (default 100, maximum 1000) and `?before={n}`, since a history that is kept forever has no natural
length limit.

**Versions written before 2.1 are not indexed.** A group's history starts at its first change under 2.1.
No backfill: the consumer that needs group history is not in production, and a backfill would have to diff
every pair of retained snapshots. (See open question 4.)

## D4. Retention per template id pattern (L2)

**Config shape.** The existing top-level fields become the defaults; ordered rules override them per id:

```
TemplateHistory__RetentionDays=90               # default; 0 = keep every version
TemplateHistory__MinVersions=0                  # default; always keep at least this many newest versions
TemplateHistory__ExpiredRuleRetentionDays=0     # default; see D6 (0 = 2.0 behaviour)
TemplateHistory__Rules__0__Pattern=promotion-*
TemplateHistory__Rules__0__RetentionDays=0
TemplateHistory__Rules__0__ExpiredRuleRetentionDays=380
TemplateHistory__Rules__1__Pattern=loyalty-*
TemplateHistory__Rules__1__RetentionDays=0
```

```csharp
public sealed class TemplateHistoryOptions
{
    public int RetentionDays { get; set; } = 90;
    public int MinVersions { get; set; } = 0;
    public int ExpiredRuleRetentionDays { get; set; } = 0;
    public List<TemplateHistoryRule> Rules { get; set; } = [];
}

public sealed class TemplateHistoryRule
{
    public string Pattern { get; set; } = "";
    public int? RetentionDays { get; set; }             // null = the top-level value
    public int? MinVersions { get; set; }
    public int? ExpiredRuleRetentionDays { get; set; }
}
```

- **Matching.** `Pattern` is matched against the template id (not the Redis key), ordinal and case-sensitive.
  `*` matches any run of characters, including none; every other character is literal. Rules are tried in
  index order and the **first match wins**; a field the matching rule leaves unset takes the top-level value
  (no merging across several matching rules). An id that matches no rule uses the top-level values, so the
  90-day default is unchanged for everything not named.
- **Validation at start** (an `IValidateOptions` like `TemplatesOptionsValidator`, `ValidateOnStart`): every
  `Pattern` non-empty, every number `>= 0`. A bad value stops the service instead of silently keeping or
  dropping history.
- **`ExpiredRuleRetentionDays` lives on the same rules** although it governs the current document, not its
  history, because both answers come from the same question ("how long does this id keep the past?") and one
  ordered table is easier to reason about than two. It has to be per pattern: a document of short-lived
  per-event rules must keep dropping them on the next write, while promotions keep theirs for a year.
- The binding must work under NativeAOT (the configuration binder source generator handles `List<T>` of a
  POCO). A test binds the env-var shape above.

**Prune rule (fixes bug 1).** On each write, after the commit, for the id's resolved
`(RetentionDays, MinVersions)`:

- `RetentionDays = 0`: prune nothing.
- Otherwise let `cutoff = now - RetentionDays`. A version is kept if **any** of these holds:
  1. it was written at or after `cutoff`;
  2. it is the highest-numbered version written before `cutoff` (it was the version in force when the window
     opened, so every moment inside the window has its version);
  3. it is one of the `MinVersions` highest-numbered versions.
- Everything else is deleted in one transaction that removes, for each pruned n, `K:v{n}`, the member n of
  `K:versions`, the field n of `K:vmeta`, and the `K:gidx` members for the groups listed in that field. The
  index and the snapshots therefore never disagree: a version listed in a group's history always has its
  snapshot.

Rule 2 uses the highest *version number*, not the highest score, so clock skew between pods cannot pick the
wrong one. Retention is resolved on every write, so a config change takes effect on each document's next write.

## D5. Group routes (L3)

| Method | Path | Does |
|---|---|---|
| GET | `v2/templates/{id}/groups/{group}` | `{"rules":[...]}` in document order. `ETag` = group ETag, `X-Template-Version` = document version. `?includeExpired=true` (D6). `404` if the document or the group has no rules |
| PUT | `v2/templates/{id}/groups/{group}` | Replace every rule of the group. Body `{"aggregationField"?: "...", "rules": [...]}`. Returns `{"version": n}`, group `ETag` |
| DELETE | `v2/templates/{id}/groups/{group}` | Remove every rule of the group, ended ones included. `204`; `404` if it has none |
| GET | `v2/templates/{id}/groups/{group}/versions` | `[{"version","updatedAt","changedBy","groups"}]`, newest first, the versions that changed the group (D3). `?limit`, `?before` |
| GET | `v2/templates/{id}/groups/{group}/versions/{n}` | `{"rules":[...]}`: the group as it stood in document version n (from `K:v{n}`). `404` if n is not retained |
| POST | `v2/templates/{id}/groups/{group}/rollback/{n}` | Restore the group as it stood at version n, as a new version. Returns `{"version": m, "rules": [...]}`, group `ETag` |

The two `GET`s that are not in the original request (the group itself, and the group at version n) are
needed: the first is where a client gets the group ETag for `If-Match`, the second answers "what were this
group's rules at version n" without the client fetching the whole snapshot.

**Group ETag and `If-Match` (decided: a content hash, not the document version).** The group ETag is the
first 16 hex characters of SHA-256 over the serialized ordered list of the group's stored rules, ended rules
included, the same construction as the rule ETag. `If-Match` on the three group writes:

- absent: last writer wins *for this group*; a lost document-version race is retried, never reported;
- `*`: the group must exist, else `412`;
- a group ETag: `412` unless the group's stored rules still hash to it.

Using the document version as the group's `If-Match` was considered and rejected: two clients editing
different groups of one document would both send the same document version, and the second would get `412`,
which defeats the purpose of group writes. With a content hash, a write conflicts only with a change to the
same group; changes to other groups move the document version, which the retry loop absorbs. An A-B-A change
(the group returns to the content the client read) is not reported as a conflict, which is correct: the
client's edit was made against what is stored.

**Group `PUT` rules.**

- Each rule in the body must have a non-empty `name` and either no `group` or `group` equal to the route's;
  it is stored with the route's group. Names must be unique in the body.
- A name already used by a rule outside this group (another group, or an ungrouped rule) is a `400` naming the
  rule and its owner. Rule names stay unique across the document, which the rule-level routes rely on.
- Every rule is compile-validated, as a document `PUT` is; any failure is a `400` per rule name, and nothing
  is written.
- An empty `rules` array is a `400` ("use DELETE"), so a client bug cannot remove a group by sending nothing.
- **Placement.** The group's rules are written contiguously, in body order, at the position of the group's
  first existing rule; the group's other rules (if they were scattered) are removed. A new group is appended
  at the end. Order across groups therefore never changes because one group was edited.
- **A missing document is created** with the body's `aggregationField` (a `400` if it is absent), in the same
  conditional commit (`K:version` not existing, or equal to the counter a deleted document left). That way two
  clients creating the first group of a new document cannot overwrite each other, which a separate "create
  the document, then write the group" sequence would allow. When the document exists, a supplied
  `aggregationField` must equal the stored one, else `400`.

**Group rollback rules.**

- Reads `K:v{n}`; `404` if not retained. Takes the rules whose `group` is the route's, in their order at n.
- If the group had no rules at n, `404` ("group not present at version n; use DELETE to remove it"), so a
  rollback never deletes a group by surprise.
- Then it is a group `PUT` of those rules (placement, name uniqueness, `If-Match`, retry). A name that another
  group owns now is a `409` naming both groups.
- Restored rules keep their `expiresAt`. A rule that has ended is restored and stays skipped on evaluate;
  one that ended longer ago than `ExpiredRuleRetentionDays` is dropped by the commit (D6), as it would have
  been by any write.

**`changedBy` (fixes bug 2).** Every write, including both rollbacks, records the caller from the
`Templates:ChangedByHeader` header (or `Unknown`). It is stored in the document, in its snapshot and in
`K:vmeta`.

**Request and response types** are registered in `AppJsonSerializerContext` (NativeAOT).

## D6. Ended rules (L4)

`V2Logic.Prune` today does two jobs, hiding on read and dropping on write. They become two functions with
different rules:

| Function | Where | Rule |
|---|---|---|
| `HideEnded(doc, now)` | `GET` document, `GET` rule, `GET` group, unless `?includeExpired=true` | hide a rule with `expiresAt <= now` (2.0 behaviour; it is the document the service serves) |
| `DropEnded(doc, now, days)` | inside the commit loop, on the document about to be committed, for every write path | drop a rule with `expiresAt + ExpiredRuleRetentionDays <= now` |

- **Evaluate and explain are unchanged**: a rule with `expiresAt <= now` never matches. Explain's reason text
  changes from `pruned: …` to `expired: …`, since the rule is no longer pruned at that point.
- With the default `ExpiredRuleRetentionDays = 0`, `DropEnded` drops exactly the rules that 2.0's write path
  drops, so documents not named by a rule behave as before. A document with a retention keeps ended rules
  through unrelated writes until the retention has passed after their `expiresAt`.
- Drops happen only when the document is written; there is no background job. A rule may stay stored longer
  than its retention if nothing writes the document; that costs space only, since it never matches.
- **`?includeExpired=true`** returns every stored rule. The rule's own `expiresAt` tells the caller it has
  ended; no extra field is added, so a document still round-trips unchanged. `GET .../versions/{n}` and
  `GET .../groups/{group}/versions/{n}` always return the snapshot as stored.
- **ETags cover stored content, not the filtered view.** The document ETag is the version; rule and group
  ETags hash the stored rules, ended ones included. A change hidden from the default view still moves them.
- **Rule `GET` now hides ended rules by default** (2.0 returned them, unlike the document `GET`). This makes
  every read route agree. A rule `PUT` to the name of a stored ended rule replaces it in place.
- **A whole-document `PUT` replaces the whole document**, ended rules included: rules the body leaves out
  are gone (their history remains). A client that edits a whole document and wants to keep ended rules reads
  it with `?includeExpired=true` first. The README says so. The alternative, carrying stored ended rules
  over into a `PUT` body that omits them, makes `PUT` not mean "replace" and was rejected; clients that need
  ended rules kept should write by rule or by group.
- A `DropEnded` that removes rules of group g during an unrelated write records that version as a change to g
  (D3), with the unrelated writer's `changedBy`. That is accurate: the group's stored rules changed then.

## Key layout after 2.1

| Key | Type | Written by | New |
|---|---|---|---|
| `K` | string | commit | |
| `K:version` | string (counter) | commit, delete | |
| `K:v{n}` | string | commit; deleted by prune and delete | |
| `K:versions` | sorted set (n by write time) | commit; prune; delete | |
| `K:vmeta` | hash (n → summary) | commit; prune; delete | yes |
| `K:gidx` | sorted set (lexical) | commit; prune; delete | yes |
| `templates:index` | set | commit; delete | |

`DeleteAsync` adds `K:vmeta` and `K:gidx` to the keys it deletes, still in one transaction. Deleting a
document deletes its history, whatever its retention (see open question 3).

## Compatibility

Wire changes are additive: new routes, a new optional query flag, a new optional `groups` field in version
summaries, two new optional query parameters on the version list. Existing Redis keys keep their shape;
two keys are added. Behaviour changes, for the CHANGELOG:

1. **`TemplateHistory__RetentionDays=0` now means "keep every version"** (2.0 treated `<= 0` as one day).
   A negative value now stops the service at start.
2. **A `PUT` with no `If-Match` can now return `409`**, after `RuleWriteAttempts` lost version races in a row.
   2.0 documented that such a write always succeeds; the README sentence changes.
3. A rule `GET` hides ended rules unless `?includeExpired=true`.
4. Explain reports an ended rule as `expired: …` instead of `pruned: …`.
5. Prune keeps the version that was in force at the start of the retention window (bug 1 fixed).
6. Rollbacks record the caller as `changedBy` (bug 2 fixed).

**Running 2.0.x and 2.1 against the same keys** (a rolling update, or rolling back to 2.0.x):

- A 2.0.x write still bumps the counter and writes `K` and `K:v{n}`, so 2.1's conditional commit stays
  correct alongside it. It writes no `K:vmeta` field and no `K:gidx` members, so versions it writes are
  missing from group histories, and the version list falls back to reading their snapshots.
- A 2.0.x write prunes by the flat 90-day rule and drops ended rules: **it deletes history and ended rules
  that 2.1 would have kept** for ids under a keep rule. Rolling back to 2.0.x is safe only while no such
  document has history older than 90 days or ended rules it must keep, or while writes to those documents are
  stopped. Orphaned `K:vmeta` fields and `K:gidx` members for versions 2.0.x pruned are harmless: readers
  skip a version whose snapshot is gone, and 2.1's next prune of that document removes them.
- Release: `version.json` goes from `2.0` to `2.1`; the first push to `main` after that publishes 2.1.0
  (versions are height-based, see the CHANGELOG).

## Storage growth (read before setting `RetentionDays=0`)

A snapshot is the whole document. Under a keep rule, every write adds one more document's worth of memory
forever, and Redis holds it all in memory. Illustration: a 300 KB document (300 rules of about 1 KB) written
100 times a month grows by about 30 MB a month, 360 MB a year, per document. Lower write rates or smaller
documents scale linearly. This does not change the design above, but it decides whether keep-forever is
affordable; see open question 1.

## Tests, per step

Every test runs in `dotnet test RuleEngine.slnx` against a real Redis (Testcontainers, as today). Names are
indicative.

**L1 (commit primitive).** `Repository` gains an internal constructor that takes the `Func<IDatabase>`, so a
test can wrap the database with a `DispatchProxy` (tests run JIT, so a proxy over `IDatabase` and
`ITransaction` is cheap to write).

- `a_commit_issues_no_write_outside_its_transaction`: the wrapper records every write command sent on the
  database itself (not on a transaction) during a commit; there are none. This is the "fault between the
  document write and the snapshot write" test: with one `EXEC` there is no such point in the client.
- `a_commit_that_fails_before_exec_changes_nothing`: the wrapped transaction throws instead of executing;
  `K`, `K:version`, `K:v{n}`, `K:versions`, `K:vmeta` are all unchanged.
- `every_version_returned_by_a_write_has_a_snapshot`: several concurrent writers mixing document `PUT` (with
  and without `If-Match`), rule `PUT` and rollback; afterwards every n from 1 to the current version has
  `K:v{n}` and a `K:vmeta` field, and every returned version number is among them.
- `an_unconditional_put_retries_a_lost_race` and `an_unconditional_put_returns_409_after_the_attempts`.

## Open questions for the owner

1. **Snapshot size under keep-forever.** Should snapshots above a size threshold be stored compressed (one
   marker byte, then Brotli or GZip; JSON of repeated rule shapes compresses several times over), or should
   history for grouped documents store only the changed groups' rules? Compression is local to `CommitAsync`
   and the snapshot reader and could ship in 2.1 or later; per-group snapshots would change L1's "a snapshot
   is the whole document" and are not proposed. Default if not answered: neither in 2.1, and the README
   carries the sizing note.
2. **Group ETag.** This note uses a content hash, because the document version would make different groups
   conflict (D5). Confirm.
3. **Delete of a keep-forever document.** `DELETE v2/templates/{id}` removes the history whatever the
   retention. Keep that (callers that need an audit trail never delete), or refuse `DELETE` for ids under a
   keep rule? Default: keep.
4. **No backfill of the group index** for versions written before 2.1. Default: none.
5. **Unconditional `PUT` can return `409`** after 4 lost races. Acceptable for bulk import, or should the
   unconditional path retry more times than rule writes? Default: the same 4.
